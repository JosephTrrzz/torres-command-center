# Torres OS security model

Updated 2026-08-25.

## Security boundaries

- Identity: Supabase Auth user.
- Tenant: organization membership, with compatibility support for legacy client assignments.
- Application: Cloudflare Function authorization for privileged operations.
- Database: RLS on every browser-accessible tenant-owned table.
- Provider: encrypted server-only credentials with minimum required scopes.

## Roles

- `owner`: full tenant administration, membership, security, billing, and destructive approvals.
- `admin`: tenant configuration and operational administration without ownership transfer.
- `operator`: agency delivery and client operations allowed by permission.
- `member`: standard client workspace contributor.
- `viewer`: read-only access.
- `client`: compatibility role for customer portal users during migration.

Permissions, not labels, are the long-term contract. Default role permissions are seeded centrally and exceptional access must be explicit and auditable.

## Authorization sequence

1. Validate the Supabase bearer token.
2. Load the active profile.
3. Resolve active organization memberships.
4. Verify the requested organization and any parent-agency relationship.
5. Check the required permission and record scope.
6. Perform privileged work server-side.
7. Write an audit event and, when asynchronous, an outbox event.

The current controlled cutover applies this sequence to Google connection/property routes, report data, team invitations, and customer invitations. A legacy profile fallback remains only for accounts without active organization memberships; once a membership is present, organization scope is authoritative.

Client provisioning and onboarding use the same server boundary. Creating a client requires `clients.manage`; agency staff may update onboarding only for client organizations in their agency, while client members may update only their own organization. Browser sessions receive scoped snapshots through `/api/onboarding` and never receive direct write grants to onboarding tables. Completion, client creation, and related lifecycle changes produce audit and outbox records.

## Invitation lifecycle

- Owners and administrators can invite agency team members through a server Function guarded by `organization.manage`.
- Agency operators with `clients.manage` can invite customers only into client organizations they can access.
- New memberships remain `invited` until the Supabase activation session is accepted.
- Acceptance activates the membership, records the accepting user, updates the invitation lifecycle, and writes an audit event.
- Raw action links are returned only to the authenticated administrator and are never stored in application tables.
- Owner access cannot be granted through the ordinary invitation form.

## RLS invariants

- A user cannot read another organization's records without a membership or explicit agency relationship.
- A client user cannot widen their own role, organization, or client assignment.
- Browser clients cannot write memberships, role defaults, invitations, audit events, provider tokens, or outbox events directly.
- Browser clients cannot write business profile, location, service, goal, or onboarding workflow tables directly; authorized Functions perform and audit those writes.
- Service-role access is permitted only inside server Functions and controlled operator migrations.
- Cross-tenant tests must cover reads and writes for each new domain table.

## Secrets and tokens

Secrets are Cloudflare production secrets or server-only variables. OAuth refresh tokens never reach the browser. Invitation tokens are generated by the identity provider and are not stored in plaintext application tables. Logs must redact authorization headers, tokens, passwords, and sensitive message bodies.

## AI safety

AI retrieval is filtered by organization before model invocation. Prompt inputs and outputs are logged with redaction and retention controls. AI can draft or recommend; actions that communicate externally, publish content, change money, change access, or delete data require user approval.

## Operational controls

- MFA is required for owners when the identity provider policy is enabled.
- Critical membership, connection, export, billing, and automation changes are audited.
- Rate limits apply to authentication, invitations, AI requests, exports, and provider sync triggers.
- Backups, retention, export, and deletion procedures are documented and tested before general availability.
